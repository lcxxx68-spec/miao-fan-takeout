# 秒饭 限时抢购压测报告

## 一、测试目的

验证限时抢购链路的两个核心结论：

1. **不超卖**：高并发下放行的请求数恰好等于库存，不多卖一件
2. **异步削峰有效**：把落库从请求线程剥离后，接口的吞吐与延迟改善多少

## 二、测试方法

| 项 | 说明 |
| --- | --- |
| 被测接口 | `POST /user/seckill/{activityId}` |
| 并发用户 | 200 个不同用户同时抢购，每个用户只发一次请求 |
| 活动库存 | 200（保证 200 个请求都有机会成功，测的是处理能力而不是抢不到的拒绝路径） |
| 对比变量 | **只切换一个开关**：`miaofan.seckill.async-enabled` |
| A 组（sync） | 请求内直接落库：查库存 → 写流水 → 扣库存 → 建订单 → 写明细 |
| B 组（async） | 请求内只做 Redis 预扣 + 投递消息，落库交给消费者 |
| 客户端 | 独立进程发起请求（应用单独进程运行） |
| 环境 | 本机 Windows、JDK 21、MySQL 8、Redis，单机测试 |

## 三、测试结果

```
BENCH mode=sync  users=200 | accepted=200 abnormal=0 | wall=4720ms qps=42.4  | avg=3036ms p50=3062ms p90=4439ms p99=4680ms max=4714ms | settle=22ms   | activityId=36
BENCH mode=async users=200 | accepted=200 abnormal=0 | wall=1385ms qps=144.4 | avg=1303ms p50=1306ms p90=1361ms p99=1378ms max=1383ms | settle=4828ms | activityId=35
```

| 指标 | 同步落库 | 异步削峰 | 变化 |
| --- | --- | --- | --- |
| 200 并发总耗时 | 4720 ms | 1385 ms | **降低 71%** |
| 接口 QPS | 42.4 | 144.4 | **提升 3.4 倍** |
| 平均响应时间 | 3036 ms | 1303 ms | 降低 57% |
| P90 | 4439 ms | 1361 ms | 降低 69% |
| P99 | 4680 ms | 1378 ms | **降低 71%** |
| 最大响应时间 | 4714 ms | 1383 ms | 降低 71% |
| 全部订单落库完成 | 22 ms | 4828 ms | 变慢（见下方代价说明） |
| 成功数 / 异常数 | 200 / 0 | 200 / 0 | 两组均无超卖、无失败 |

## 四、结论与代价

**结论一：不超卖。** 两组都是 200 个请求全部成功、0 异常，且活动已售数量与 Redis 剩余库存相加恒等于总库存。Redis + Lua 的原子扣减在这里起到了决定作用。

**结论二：异步削峰把接口延迟压下来了。** 同步模式下每个请求都要等数据库写完才能返回，而本机 Druid 连接池默认只有 8 个连接，200 个并发请求在连接池上排队，P99 被拖到 4.7 秒；异步模式把落库移出请求线程后，同样 200 并发下单，P99 降到 1.4 秒。

**代价：订单是延迟生成的。** 异步模式下"用户拿到响应"与"订单真正落库"之间隔了约 4.8 秒。这在小程序端表现为"排队中，请稍后查询结果"，由前端轮询获取最终结果。这个代价是可接受的：用户不需要盯着转圈等数据库，而系统获得了数倍的吞吐。

## 五、复现方式

```powershell
powershell -File scripts\bench-seckill.ps1
```

脚本会自动构建 jar、分别以两种模式启动应用、各跑一轮压测，最后输出两条对比数据。压测数据用完即删，不会污染演示数据。

## 六、测试过程中的两次方法修正（值得记录）

**第一次：把压测客户端和服务放在同一个 JVM 里，结论是错的。**

最初的压测写成 `@SpringBootTest` 集成测试，客户端与被测服务在同一个 JVM、同一组 CPU 上跑。结果是异步模式**反而更慢**（平均 2176ms vs 同步 1285ms）——因为异步省下的时间被两个角色争抢 CPU 的开销吃掉了。这个测法根本无法证明削峰的价值，所以整组数据直接废弃。

修正后：应用单独进程运行，压测客户端在另一个进程，测出的才是真实的接口表现。**教训是压测客户端不能和被压测系统共享资源。**

**第二次：SQL 日志把数据拖低了。**

项目原本把 mapper 的日志级别设成 DEBUG，每条 SQL 都同步写控制台。同步写日志本身就是一个瓶颈，会让两个模式的数字都被压制。两组统一关掉 SQL 日志后再测，才是可比的数据。

## 七、说明与局限

- 这是**本机单机**压测数据，不构成生产环境的性能承诺，面试时应如实说明
- 200 并发已经足以让本机连接池饱和，真实场景应按压测机与服务器分离、逐步加压进行
- 压测脚本与客户端代码都在仓库里（`scripts/bench-seckill.ps1`、`SeckillBenchmarkClient.java`），任何人可以复现
